# TESTING TASK — Validate the Automation Without Assuming Real Hardware or Services

You are testing an existing PC + Android automation repository.

## CRITICAL ENVIRONMENT CONSTRAINT

You do NOT have guaranteed access to:

* a physical Android device
* ADB
* Replit
* a real browser session
* a live temp-mail.org inbox
* a live 1secmail mailbox
* a live PC UI environment
* the user's actual execution environment

Therefore:

**Do not claim an integration test passed unless you actually had the required external resource.**

Do not fabricate successful browser, Android, ADB, Replit, or email-provider results.

Instead, build a layered test suite that can run completely offline.

---

# 1. FIRST INSPECT THE PROJECT

Before writing tests:

1. Read the repository structure.
2. Read `steps.md`.
3. Inspect the relevant screenshots in `attached_assets/`.
4. Read the existing implementation.
5. Read existing tests.
6. Identify which components are:

   * pure logic
   * external-service dependent
   * browser dependent
   * ADB/device dependent

Document the result before making assumptions.

---

# 2. TESTING LAYERS

Organize testing into four layers:

```text
LAYER A
Pure offline unit tests

LAYER B
Mocked provider/browser/ADB tests

LAYER C
Simulation/state-machine tests

LAYER D
Real-environment integration tests
```

Only Layers A–C are expected to run in the current environment.

Layer D should be clearly marked:

```text
NOT RUN — required external environment unavailable
```

---


# 13. RETRY / TIMEOUT TESTING

Every retry loop must have a test proving that it terminates.

Test:

```text
email polling never succeeds
```

```text
page never reaches expected state
```

```text
Android login keeps returning an error
```

```text
browser action repeatedly fails
```

Assert that each ends in a bounded failure state.

There must be no infinite loops.

# 18. NO FAKE INTEGRATION RESULTS

Never write:

```text
Android test passed
```

unless an actual Android device was available.

Never write:

```text
Replit login passed
```

unless Replit was actually accessed.

Never write:

```text
temp-mail integration passed
```

unless the actual provider was contacted.

Use explicit result categories:

```text
PASS — actually executed
PASS — mocked/simulated
NOT RUN — external environment unavailable
FAIL — executed and failed
BLOCKED — prerequisite unavailable
```

# 21. FINAL ACCEPTANCE CRITERIA

The testing task is complete when:

1. Offline unit tests exist for all pure logic.
2. Email providers have mocked tests.
3. Browser operations have mocked tests.
4. ADB operations have mocked tests.
5. Full PC flow has a deterministic simulation.
6. Full Android flow has a deterministic simulation.
7. Retry/timeout paths are tested.
8. Security-challenge paths are tested.
9. Reference screenshots and `steps.md` are used for structural verification.
10. No fake real-device/browser results are reported.
11. All unavailable external tests are explicitly marked.
12. A final `TEST_REPORT.md` is produced.
