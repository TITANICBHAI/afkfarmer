## 3. Preflight is wrong for the offline-development model

The correct model is:

```text
preflight
```

means local/offline readiness.


means "is this machine actually capable of a real run?"

## 7. The 1secmail verification implementation is too optimistic

This part deserves another pass.

The provider:

```text
get message
→ extract Replit URL
→ requests.get(verification_url)
→ inspect response text
→ require a success phrase
```

That assumes the HTTP response body itself will contain a recognizable success message.

A verification endpoint may instead:

```text
redirect
render client-side content
return a generic HTML page
close a session
```

So:

```python
status_code == 200
```

is not necessarily equivalent to:

```text
Replit account is verified
```

And requiring:

```text
"email verified"
```

in the raw response body may produce a false failure even when the verification actually succeeded.

This provider needs a more carefully defined verification contract.

## 8. The verification URL is persisted in `state.json`

`main.py` does:

```python
self.state["verification_link"] = self.pc.verification_url
```

That URL may contain a one-time verification token.

You already correctly say in your implementation docs that verification links are sensitive.

So there is an inconsistency:

```text
docs:
verification URL = sensitive

code:
persist verification URL in checkpoint state
```

I'd change the checkpoint to record something like:

```json

  "verification_completed": true
}
```

and avoid storing the full URL unless there is a demonstrated need.

## 9. Manual takeover currently has too much power

This part is potentially dangerous from a state-machine perspective:

```text
[m]anual takeover then continue
[s]kip stage
```

Both eventually advance the checkpoint.

That means:

```text
stage failed
→ user presses m
→ system marks stage complete
```

without verifying the actual postcondition.

Same with `skip`.

That's okay as an explicitly operator-controlled escape hatch, but it should **not pretend that the stage succeeded**.

Better:

```text
AUTOMATION_SUCCESS
MANUAL_COMPLETION
SKIPPED
```

as three different outcomes.

Then later stages know the difference.
